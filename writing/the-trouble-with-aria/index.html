The Trouble With ARIA.

More attributes don't make a better interface. Understanding semantics does.

During my time as a lead accessibility developer, I reviewed markup and interactive functionality across nearly 100 websites. One of the most consistent problems I encountered was not developers misusing ARIA. It was developers omitting it when their implementations actually needed it.

Interactive controls changed state without communicating those changes to assistive technology. Search results updated visually without meaningful announcements. At other times, ARIA attributes were added to native elements that already provided the semantics.

Both patterns pointed to the same issue: accessible markup requires understanding what the browser already communicates, what information is missing, and how users interact with the component.

No ARIA is better than bad ARIA. That is not an argument against ARIA. It is an argument for communicating the right information, in the right way, at the right time.

01 / 06

The missing information

Consider a simple expandable component. Visually, a user clicks a button, a panel opens, and more content appears. But what does a screen-reader user learn from that interaction?

A native button already communicates its role and supports keyboard activation. It does not automatically announce whether a separate panel is expanded or collapsed. That is where aria-expanded becomes valuable: it communicates information that might otherwise only be available visually.

The same principle applies to more involved interactions. Dynamic search results may need an announcement. Opening a modal changes the current interaction context. A carousel needs understandable navigation and a way to identify the slide being presented.

The question is not simply whether an attribute exists. It is whether people using assistive technology can access the same meaningful information as someone using the interface visually.

That became a central part of my accessibility reviews: understanding what a component was doing, which information the browser already provided, and what users still needed to know.

02 / 06

When ARIA gets in the way

ARIA can supplement the accessibility information exposed by HTML. But adding it without understanding its purpose can introduce conflicting semantics, misleading names, and unexpected behavior.

Redundant roles and unnecessary attributes

A native <button> already has a button role. A <nav> already exposes a navigation landmark. An <h2> already conveys a heading and its level. Repeating those semantics with ARIA generally adds no value.

Redundant ARIA does not necessarily break an interface immediately. But it adds maintenance overhead, creates opportunities for conflict, and can reinforce the mistaken assumption that semantic HTML needs extra attributes to be accessible.

Making non-interactive elements interactive

I also encountered <div> and <span> elements used as controls when a native element would have been more appropriate. A role="button" may identify a custom element as a button, but it does not supply focusability or Enter and Space activation by itself.

A real <button> provides the expected semantics and keyboard behavior. Often the more accessible choice is also less code to write and maintain.

Accessible names versus visible labels

The relationship between aria-label and the HTML <label> element was another source of confusion. A visible label associated with a form control supports sighted users and contributes to its accessible name. aria-label can provide a name where visible text is not available, such as on an icon-only button.

But an unnecessary aria-label can override meaningful existing text and even produce a mismatch between what people see and what assistive technology announces. The first question should be whether an appropriate accessible name already exists.

Hiding content without considering focus

Misused aria-hidden="true" can remove content from the accessibility tree while leaving its controls visible or keyboard-focusable. That creates a situation where focus can land on something a screen reader has been instructed to ignore.

Visibility, focus behavior, and accessibility semantics must describe the same state, especially in dialogs, menus, and carousels.

Recreating heading semantics

A combination of role="heading" and aria-level can be valid when native heading markup is not feasible. But when <h2> is available, it is clearer and easier to maintain than recreating its semantics.

Sometimes the solution is adding ARIA. Sometimes it is removing unnecessary ARIA. Sometimes it is choosing a better HTML element. Good accessibility engineering means knowing the difference.

03 / 06

Start with native HTML

One of the simplest accessibility principles is also one of the most effective: use the HTML element that already represents what you are building.

Buttons, links, labels, form controls, headings, and landmarks provide built-in semantics and behaviors that are easy to lose when we replace them with generic elements.

A <div role="button" tabindex="0"> can advertise an intention, but it still requires custom JavaScript to handle expected button activation. A native <button type="button"> supplies that behavior immediately.

Use links for navigation and buttons for actions. Associate visible labels with form controls. Use real headings to communicate document structure.

The more accurately HTML describes the interface, the less work ARIA needs to do—and the fewer opportunities we create for bugs.

04 / 06

When ARIA earns its place

Starting with semantic HTML does not eliminate the need for ARIA. Modern interfaces can change state in ways that HTML alone does not always communicate.

Expandable content

A disclosure button may reveal or hide a panel. aria-expanded can communicate that state, but the value must match what is actually visible. Announcing an expanded state after the panel has closed is misleading.

Dynamic search and live regions

When results update without a page navigation, screen-reader users may need to hear that the search completed, how many results were found, or that no results matched. A thoughtfully implemented live region can convey those changes without moving focus.

But announcing every change can be just as frustrating as announcing nothing. Timing, wording, and frequency are part of the implementation.

Modal dialogs and focus

A dialog needs an accessible name and an understandable interaction context. When a modal opens, focus should move into it; while it is active, keyboard users should not inadvertently navigate background controls. On close, focus should generally return to a logical place.

The native <dialog> element and showModal() provide much of the expected modal behavior, but the surrounding focus experience and labeling still deserve testing.

Carousels and changing slides

Carousels need clear controls, meaningful slide identification, and thoughtful announcements. Interactive controls inside inactive slides must not remain unexpectedly available in the keyboard navigation order.

Autoplay adds another concern: people need enough time and control to read and interact without movement or repeated announcements interrupting them.

Across all of these patterns, one principle connects the engineering work: when an interface changes state, its accessibility information and behavior should change with it.

05 / 06

Passing an audit doesn’t mean passing the experience

One of the most valuable lessons I learned through accessibility quality assurance was that automated testing can tell you a great deal about a website, but not everything about using it.

As a lead accessibility developer, I tested against WCAG 2.1 AA using Lighthouse, the AQA Chrome extension, VoiceOver, and manual keyboard navigation across nearly 100 websites.

Automated checks helped identify detectable missing names, invalid ARIA, and structural problems. But a component could appear sound in an automated report while still being difficult or impossible to use.

The keyboard tells a different story

A scan might recognize a labeled dialog, but does focus enter it when opened? Can users navigate its controls in a sensible order? Does focus stay within the modal? Does it return logically when the dialog closes? Those behaviors require interactive testing.

A screen reader reveals what markup communicates

VoiceOver helped me evaluate whether exposed information was not just technically present but useful. A dynamic search might update perfectly visually while a screen-reader user hears no indication of change—or hears too many confusing announcements.

The goal is not simply to make the screen reader say something. It is to convey meaningful information when users need it.

Semantic HTML is the foundation. ARIA fills meaningful gaps. Automated tools catch many issues. But keyboard and assistive-technology testing reveal how those decisions work together in practice.

06 / 06

Better accessibility starts with better engineering decisions

After reviewing and remediating accessibility issues across so many websites, one thing became clear: the most effective improvements often begin long before the audit.

They begin when someone chooses a native button instead of recreating one with a <div>; when a form field gets a meaningful visible label; when a disclosure communicates its current state; and when a modal is built with focus management in mind.

That is why I began advocating for accessibility and ARIA checks as part of regular code reviews, rather than waiting for formal AQA to catch every problem.

Over time, I began seeing developers address accessibility concerns in tasks that were not specifically assigned as remediation work. That was especially encouraging: accessibility was becoming part of everyday engineering judgment.

No ARIA is better than bad ARIA. Native HTML should do as much of the work as possible. And when ARIA is needed, it should communicate something meaningful and accurate.

Ultimately, accessibility is not about how many attributes we add or how many automated checks we pass. It is about whether people can actually use what we have built.

The Frontend Doesn’t End at Twig.

Why building better Drupal interfaces starts with the content model.

I've spent a significant portion of my career building websites in Drupal, and I've always found it interesting how often frontend work is treated as something that starts after the backend is finished.

The content types are created. The fields are configured. Paragraphs and Views are established. Then the frontend developer receives the templates, CSS, and JavaScript work.

Except that's not how I've typically worked. I built the content architecture supporting my own frontend implementations: content types, taxonomies, fields, Paragraphs, Views, and reusable components.

For me, those weren't separate backend tasks. They were part of building the frontend.

The frontend doesn't begin when Drupal finishes preparing the data. It begins when we decide how that data should be structured in the first place.

01 / 09

A component starts with a conversation

One of the most important parts of building a Drupal component happens before I create a content type, configure a field, or write a line of Twig. It starts with understanding what the component is supposed to accomplish.

Throughout my Drupal work I collaborated with content authors and project managers to clarify requirements, editorial needs, design expectations, and what the component was intended to do. What information is required? Which variations matter? Will editors supply cards manually, curate existing content, or rely on a query? What happens when real content differs from the design?

A design showing an image, heading, description, and link doesn't answer whether the image is required or whether the component needs to work in multiple contexts. Those are architecture decisions, not styling details.

Once we understood the requirements, I designed the Drupal structures—fields, Paragraphs, references, taxonomy relationships, or Views—with the eventual component behavior and layout in mind. Then I built the Twig, CSS, JavaScript, and interaction layer around that model.

A good Drupal component isn't simply a design translated into Twig. It's the result of understanding the content, the editor's workflow, and the visitor's experience together.

02 / 09

Content architecture is frontend architecture

Content types, fields, taxonomies, entity references, and view modes can look like backend concerns. But each directly affects the interface we can deliver.

Consider an article listing. Is the description manually entered, derived from body content, or supplied by a display formatter? Is its category a taxonomy term or an arbitrary string? Does the collection contain references to published content, and what happens when a referenced item becomes unpublished?

These decisions change how reliably we can filter, reuse, and update content. A taxonomy reference supports meaningful relationships; a manually typed category can look identical in the browser while offering none of the same consistency.

Model information, not screenshots

It's easy to build fields around the exact three cards in a design. But are those three manually created cards, references to articles, or results selected by a View? Will they appear elsewhere? Should authors control the order? The answers shape the model.

Good content architecture gives the frontend predictable information without unnecessarily restricting how it can be presented.

03 / 09

Paragraphs are powerful. Boundaries make them useful.

Paragraphs can let editors assemble structured pages using reusable blocks instead of relying on a single body field. That flexibility is valuable—but I've seen a Paragraph that becomes slightly different in many places turn into a maintenance burden.

First one context needs a different image position, another needs an eyebrow, another a background variation, another a different mobile arrangement. Each change looks too small to justify a new type, so the existing one gains another field and another template condition.

In a CMS, every variation becomes part of the editing interface, stored content, rendering logic, styling, and testing requirements. Once widely used, those decisions become difficult to undo without affecting existing pages.

Editors need meaningful control, not a maze of unsupported combinations. Separate purpose-built components can still share underlying styles, tokens, and smaller templates.

Reuse doesn't require every visually similar component to share the same content model.

04 / 09

Views are part of the user experience

Views does much more than prepare a set of entities for display. Filtering, sorting, contextual relationships, exposed filters, and pagination shape how people find and use content.

Think about a resource library. Can visitors filter by taxonomy topic, search by keyword, sort by date, and understand what happens when the filters produce no results? How do the controls behave when pagination changes or content updates dynamically?

Those are frontend experience questions whose answers depend on query configuration and content structure. CSS alone can't solve them.

When I built listings, I needed the presentation and the data behavior to agree: taxonomy that matched the filters, sorting that matched the promise of the interface, and semantic controls that communicated results.

Configuring a View can be part of implementing the frontend, not merely a backend handoff.

05 / 09

Twig should render, not untangle

Twig gives Drupal theming a clear place to express markup. But a template shouldn't have to compensate for every unresolved decision in the content architecture.

Some presentation conditions belong in Twig. An optional image may need a conditional, and a supported layout variation may need a modifier class. But complicated nested lookups, fragile assumptions about field indices, and sprawling special cases can signal that the component lacks a predictable data contract.

Drupal's render arrays, field display configuration, and preprocess layer can help clarify what templates receive. Those render structures also carry cacheability and attachment information, so they should not be flattened thoughtlessly.

A simple template is often the outcome of decisions made much earlier. If the Twig is fighting the data, the problem may not be in Twig.

06 / 09

Building components from both directions

I didn't treat the Drupal model and frontend implementation as separate systems. They informed each other as the requirements became clearer.

A design might suggest a simple image field, while editorial discovery reveals that an existing media entity should be referenced. A card collection might initially look manual, then turn out to need dynamically selected articles. A layout offering many variations might really need just two carefully defined options.

The useful starting question is: what is this component responsible for? Presenting one entity, curating a collection, retrieving matching content, or enabling a particular interaction?

Authors understand the content workflow, PMs help define requirements, design establishes presentation intent, and engineering translates those decisions into a maintainable model and interface.

The strongest component architecture comes from connecting those perspectives before implementation decisions harden.

    07 / 09

    The editor is also a user

    We usually evaluate frontend usability from the visitor's point of view. CMS-driven websites also have another interface: the one content authors use to create and maintain the pages.

    A beautiful component isn't successful if editors have to decipher vague field labels, duplicate content, or manipulate conflicting options to make it look right. Conversely, a simple editor form is not enough if the frontend can't reliably support the design.

    Good defaults, intentional choices, clear field guidance, and reusable content relationships help authors do their work. Unsupported or inaccessible combinations shouldn't become easy to create just because another checkbox is technically possible.

    The visitor should understand the interface. The editor should understand how to create it.

    08 / 09

    Better architecture means less corrective code

    A complicated selector can exist because one component supports too many variants. A Twig file can grow conditional after conditional because the data model is unclear. JavaScript can end up compensating for markup that doesn't express the interaction properly.

    Not every implementation problem comes from the content model. But making structural decisions deliberately often reduces the corrective logic required later.

    Focused components, consistent relationships, and predictable display modes make it easier to understand a change's impact—particularly on content-heavy sites with long histories and many contributors.

    The payoff isn't glamorous. It's fewer surprises when requirements evolve.

    09 / 09

    The frontend doesn’t end at Twig

    I don't think every frontend developer needs to own every Drupal configuration decision. Different teams divide responsibilities differently, and those boundaries can be useful.

    But on my projects, defining the content model with authors and PMs and then building the frontend was one connected responsibility. That context let me understand why the structure existed and how it needed to work in the browser.

    Drupal frontend engineering can span content architecture, editorial experience, component design, Twig, CSS, JavaScript, and accessibility. Those aren't unrelated concerns; they're pieces of one user experience.

    The frontend doesn't end at Twig. And some of the most important frontend work happens long before Twig begins.

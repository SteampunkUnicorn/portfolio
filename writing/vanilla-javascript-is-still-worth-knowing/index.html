Frontend development has a habit of reinventing itself. Frameworks rise and fall, build tools evolve, and approaches once considered best practice are replaced by something new.

After more than 15 years working through those changes, I’ve learned that the most valuable frontend skills aren’t tied to a particular framework. They’re rooted in understanding HTML, CSS, JavaScript, the DOM, browser behavior, and the web’s native APIs.

Frameworks can be excellent tools. But an abstraction is most useful when you understand what it abstracts away. Knowing a framework prepares you to use that framework. Knowing the platform prepares you to adapt.

01 / 12

We’ve started treating frameworks as prerequisites

Look through frontend job descriptions and you’ll find an enormous emphasis on React, Angular, Vue, and their associated tools. That makes sense when a company needs someone familiar with its stack. But framework experience shouldn’t be treated as a substitute for frontend fundamentals.

Knowing how to render a component doesn’t necessarily mean understanding event propagation. Knowing a component library doesn’t guarantee a grasp of semantic HTML, keyboard interaction, or accessible names. Knowing a build tool doesn’t automatically mean understanding what the browser receives.

The strongest frontend engineers move comfortably between these layers. They can use their framework and still reason about the platform it runs on.

02 / 12

When learning a framework comes before learning JavaScript

I think coding bootcamps have created genuinely valuable opportunities. They make software development more accessible to people who may not have the time, money, or circumstances for a traditional degree. Structured learning, hands-on projects, and a quicker path to creating applications can make a real difference.

But accelerated curricula can leave gaps, particularly when the focus is getting students productive in a popular framework before they have a strong grasp of JavaScript itself.

A developer might know how to write React components and hooks yet struggle when an object is mutated unexpectedly, a closure captures an old value, or asynchronous operations complete in an unexpected order. Those aren’t React problems. They’re JavaScript and application-logic problems.

When something breaks, it’s tempting to look for a framework-specific explanation. But sometimes the bug exists a layer below the framework. If you only know the patterns you were taught, debugging can become a frustrating search for the right snippet instead of an investigation of what the code is doing.

This isn’t an argument against bootcamps or the developers who graduate from them. It’s an argument for giving fundamentals greater weight. There’s a difference between learning to reproduce a working example and learning to diagnose an unfamiliar one. Professional development asks for both.

The goal shouldn’t simply be to teach someone how to build an application using today’s popular framework. It should be to develop engineers who can understand, debug, and maintain applications regardless of the framework involved.

const toppings = ["cheese", "pepperoni"];
const updated = toppings;
updated.push("mushrooms");
console.log(toppings);
What's printed to the console?
Select an answer, then check it.

Both variables reference the same array. push() mutates that array, so toppings includes the new value. This is JavaScript reference behavior, not a framework bug.

const updated = [...toppings, "mushrooms"];

Copying the array produces a new reference. That's especially important when a rendering strategy relies on identity changes.

03 / 12

There will always be another framework

If there’s one thing more than 15 years of frontend development has taught me, it’s that the ecosystem never stands still. New frameworks appear. Build tools are replaced. Practices once described as revolutionary become ordinary—or disappear.

That change is often healthy. It brings new capabilities and better ways of working. But it also means that building your entire skill set around one particular technology can be limiting.

JavaScript knowledge transfers between application frameworks. CSS fundamentals—the cascade, layout, responsive behavior, and specificity—remain useful even as styling methodologies change. Semantic HTML lets you inspect any framework’s output and recognize when the structure or accessibility is wrong.

Those skills help you look past unfamiliar syntax and recognize familiar problems: rendering, state, events, asynchronous work, layout, and interaction. A new framework becomes something to evaluate and learn, not an entirely new way to think.

You don’t need to chase every trend. You do need enough grounding to recognize which new tools are worth learning and which problems your existing knowledge can already solve.

Learn the framework and you’re prepared for the current stack. Learn the platform and you’re prepared for the next one.

04 / 12

The browser is more capable than we remember

The DOM API creates and updates elements. Fetch handles HTTP requests. Intersection Observer and Resize Observer respond to visibility and size changes. Native inputs bring semantics and validation. The <dialog> element supports real modal interactions. CSS handles sophisticated layout and responsive design.

None of that eliminates frameworks. It changes when a dependency earns its place. For a small self-contained interface, a handful of state transitions may not justify an entire framework and its tooling.

Working directly with these APIs is also an opportunity to learn what the browser already handles for us—and what we still have to build.

05 / 12

Working without a framework makes decisions visible

One reason I enjoy independent vanilla JavaScript projects is that the architecture becomes explicit. How is state represented? Which changes require a DOM update? What do events mean? Which rules belong to the application rather than the view?

My Pizza Builder is a useful example. A user chooses a size, crust, sauce, and ingredients. Some categories allow one selection; others allow several; proteins have a limit. The visual pizza needs to agree with the data.

That’s a state-management problem before it’s ever a framework problem. A framework can help render state, but it can’t determine the product rules for you. Understanding the separation between state, events, and rendering makes those rules easier to test and carry into any architecture.

06 / 12

Less abstraction can mean more clarity

Abstraction helps teams organize work and reduce repetition. But not every abstraction pays for itself. Some libraries eliminate meaningful complexity; others bring configuration, dependencies, build requirements, and conventions to a very small problem.

I’ve worked on applications large enough to justify shared rendering models and team-wide architecture. I’ve also built experiments that simply needed a module and a few event handlers.

Before adding a layer, I want to know what problem it solves, what it costs to maintain, and whether the next developer will understand the result.

The goal isn’t the fewest lines of code. It’s a system that remains as understandable as its requirements allow.

07 / 12

Vanilla JavaScript isn’t automatically simpler

There’s an important counterargument: vanilla JavaScript can become difficult to maintain when a growing application accumulates scattered event listeners, duplicated rendering logic, and unclear ownership of shared state.

Native code isn’t automatically faster, more accessible, or better organized. You still need module boundaries, testing, cleanup, and conventions. An accessible component still requires the right semantics and behavior.

For a large application with many contributors, the right framework may replace a lot of custom infrastructure. That can be a very good trade. The point is to make the choice deliberately, not by default.

08 / 12

Accessibility starts below the framework

A button still needs to behave like a button, a form control needs an accessible name, and an opening dialog needs sensible focus management—whether the code was written in React, Vue, or plain JavaScript.

In accessibility reviews, many problems I encountered weren’t caused by a framework. They were misunderstandings of native semantics, keyboard interaction, focus, or assistive-technology communication.

Knowing the platform lets you inspect what a component actually renders rather than assuming a library guarantees accessibility. A framework doesn’t change the fundamentals; it changes how we organize their implementation.

09 / 12

Performance is a platform concern

Frameworks can optimize some rendering tasks. They cannot make unnecessary JavaScript, oversized assets, expensive main-thread work, or unstable layouts cost nothing.

Every application ultimately runs under browser constraints. JavaScript execution takes time. DOM changes may trigger style calculation and layout. Images without reserved dimensions can move content unexpectedly.

Understanding the platform makes performance easier to diagnose and measure rather than relying only on framework-specific optimization advice. Vanilla JavaScript doesn’t automatically win benchmarks; the implementation and workload matter.

10 / 12

Learning the platform makes frameworks easier to learn

Events, closures, modules, promises, rendering, and state are transferable concepts. Frameworks express them through different APIs and architectures, but the underlying problems remain recognizable.

That’s what makes foundations so valuable over a long career. Instead of building an identity around a specific framework’s conventions, I can connect a new tool to what I already know about application behavior and the browser.

Knowing the platform isn’t the opposite of learning modern tooling. It’s what makes learning modern tooling more meaningful.

11 / 12

Building to learn, not just to ship

Some of my favorite development work happens when I build simply to explore a problem: a pizza builder, a data playground, a component system, or an interface experiment.

These projects give me room to investigate native APIs, state transitions, accessible behaviors, and DOM updates without recreating the complexity of a large production stack.

For me, that isn’t nostalgia. It’s an exercise in understanding the medium—and a way to bring sharper judgment to framework-based work.

12 / 12

Frameworks come and go. Fundamentals carry forward.

I don’t think frontend development should return to a world without frameworks. They solve real problems, establish structure, and make complex applications manageable.

But frameworks aren’t the foundation of frontend engineering. HTML gives content structure and meaning. CSS defines presentation and adaptation. JavaScript provides the logic and behavior that makes interfaces interactive.

The tools we use to work with those technologies will keep changing. And they should. Progress means finding better ways to solve problems.

After more than 15 years watching the ecosystem evolve, I’ve come to value the skills that remain useful regardless of which stack is fashionable.

Frameworks come and go. Fundamentals carry forward.

That’s why vanilla JavaScript—and the web platform it works alongside—is still worth knowing.
